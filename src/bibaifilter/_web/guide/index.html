Guide

What BibAIFilter does, what it records and how to report it.

Two tasks

Relevance score (1–7). Ranks records by how relevant they are to a topic, which can be a whole research question rather than a keyword. Useful to order a large set so that the most relevant records are read first.

Eligibility screening. Applies explicit inclusion and exclusion criteria to title and abstract and answers include, exclude or uncertain with a reason. “Uncertain” keeps the record, because missing a relevant study is worse than reading an irrelevant one.

If your file has an include/exclude column, recall, precision, ROC AUC and work saved over sampling (WSS@95) are computed, next to a BM25 keyword baseline on the same records.

What is logged for every call

  • requested model and the model named in the provider's response (mismatches flagged)
  • the parameters actually sent — e.g. “temperature: not sent (model rejects temperature)”
  • every HTTP attempt with status and waiting time; at most 5 attempts, only for rate limits, server errors and timeouts
  • finish reason, raw answer, parse status, tokens (including reasoning tokens), latency and estimated cost
  • the prompt's SHA-256 and the record's content hash; the run manifest stores tool, Python and package versions and the input file's SHA-256

Answer statuses

okThe answer was exactly the expected value (structured JSON or a bare number/decision).
extractedThe value was the only candidate in a longer answer. Valid, but flagged.
truncatedThe output-token limit cut the answer (often because reasoning used the budget). No value.
emptyThe visible answer was empty. No value.
unparsable / ambiguousNo value, or more than one candidate value, in the text. No value — the first number is never taken.
out_of_rangeA number outside the 1–7 scale. Not clamped. No value.
refusedBlocked by the provider's safety system. No value.
errorNetwork, HTTP or provider error after the allowed retries. No value; can be retried with Resume.
skippedThe record has neither title nor abstract.

Good practice

  • Run a small trial first (“only the first N records”) and read the call log.
  • Use at least 3 repetitions to see how stable the answers are.
  • For reasoning models, set a low reasoning level for scoring, or keep a generous token limit — limits include reasoning tokens.
  • Report the run manifest (model id, served model, parameters sent, prompt hash, dates) in your methods section.
  • Use LLM output to prioritise and support human screening, not to replace it.

Privacy

Each call sends the record's title, abstract and keywords to the selected provider. Check the provider's data-use terms and the licence of your database. Free tiers may use inputs for training. With Ollama, nothing leaves your computer. API keys are stored locally and never written to run files.

Where your work is saved

Everything lives in your workspace folder (default ~/BibAIFilter, change it under Settings): uploaded files in datasets/, one folder per run in runs/ with the manifest and the full call log, and finished results in exports/ — or in the folder you chose when starting the run. Back up or share the run folder to let others check your results.

Command line

bibaifilter                  # open this interface
bibaifilter run spec.json    # same run without the interface (scriptable)
bibaifilter models           # model catalogue and parameter rules
bibaifilter check openai gpt-6-luna   # one test call
bibaifilter baseline file.xlsx --query "topic" --label-col included
BibAIFilter is open source (GPL-3.0). Every provider call is logged in the run folder; API keys stay on this computer.
